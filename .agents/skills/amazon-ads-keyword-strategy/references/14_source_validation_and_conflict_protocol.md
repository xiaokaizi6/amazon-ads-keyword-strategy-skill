# Source Validation And Conflict Protocol

本协议用于处理用户后续提供的广告优化讲义、课程文件、文章、表格、截图转录和其他资料。目标不是选出一个听起来最合理的观点，而是建立可追溯、可复核、保留不确定性的主张审查流程。

## 1. 适用范围

当任务包含新增资料、更新业务规则、判断某种打法真伪，或多个来源观点冲突时使用本协议。只做具体账户诊断且没有新增知识来源时，可直接使用现有业务 references，但仍要说明数据缺口和置信度。

## 2. 来源登记

每个来源至少记录：

- `source_id`
- 文件名或 URL
- 标题
- 作者或机构（未知则明确写 unknown）
- 发布日期与获取日期
- 版本或快照日期
- 来源类型：Amazon 官方、法规/标准、一手账户实测、独立研究、讲师观点、案例帖、评论、转载
- 适用 marketplace、广告产品、产品阶段和时间范围
- 内容哈希或其他稳定标识
- 可读性问题、缺页、图片未识别等限制

重复、转载或共同引用同一上游材料的来源要归入同一 `evidence_cluster`，不能重复计票。

## 3. 主张拆分

把资料中的重要说法拆成可独立判断的原子主张。每条主张至少记录：

- `claim_id`
- `source_id` 和原文位置
- 简短原文证据
- 规范化主张
- 主张类型：平台事实、政策合规、指标定义、因果机制、经验阈值、操作建议、案例观察、预测
- 适用条件和例外
- 时间敏感性
- 支持证据、反对证据和缺失证据
- 判断状态、置信度、复核日期

不得把同一段中的多个因果、阈值和动作合成一个不可验证的大主张。

## 4. 必须交叉验证的范围

对每条重要主张检查：

1. `data/raw/` 中全部相关原始来源。
2. `data/processed/amazon_ads_skill/` 中的 rules、cases、conflicts、counterexamples 和 source index。
3. 用户在本项目上传且本轮纳入范围的全部资料。
4. 对平台功能、政策、术语和可能变化的机制，检查当前 Amazon 官方一手资料。
5. 对效果型说法，检查产品阶段、类目、站点、样本量、时间窗、毛利、预算、广告目标和账户实测数据是否可比。

必须输出覆盖记录，包括：范围内来源总数、已检查数、未检查列表及原因、检索词/claim IDs、使用的 processed 文件和外部核对日期。没有覆盖证据时，不得声称检查了“所有文档”。

## 5. 证据优先级

证据强弱不能只按数量判断。通常优先级如下：

1. 当前适用的 Amazon 官方政策、产品文档或可复现的平台行为。
2. 定义清晰、样本和方法透明的一手数据或受控测试。
3. 多个相互独立、条件相近的账户案例。
4. 有条件、推理和限制的专业讲义或教程。
5. 单个案例、经验阈值或未披露数据的方法论。
6. 评论、转述、营销话术和无证据绝对说法。

官方资料能确认功能和政策，但不自动证明某个运营策略在所有类目有效；账户案例能说明发生过什么，但不自动证明平台因果机制。

## 6. 判断状态

| 状态 | 使用条件 |
| --- | --- |
| `supported` | 有适用范围一致的可靠证据支持，且没有同等级的实质反证。 |
| `confirmed_error` | 与更高等级且当前适用的证据直接冲突，或被可复现数据明确证伪。必须引用反证。 |
| `outdated` | 在原时间点可能成立，但已被平台、政策、功能或市场变化替代。 |
| `unsupported` | 来源未提供足够证据，且交叉验证没有找到可靠支持；不等于已证伪。 |
| `context_dependent` | 不同条件下可能成立或失败，不能泛化为统一规则。 |
| `disputed` | 独立且相对可靠的证据存在未解决冲突。 |
| `unresolved` | 当前证据或可比数据不足，无法判断。 |

`confirmed_error` 是高门槛结论。不得仅因观点与现有 skill 不一致、来源少、措辞激进或暂时找不到支持就使用。

## 7. 冲突处理

对于 `context_dependent`、`disputed` 或 `unresolved` 主张，全部有意义观点都要保留，并按以下结构输出：

1. View A 与证据、来源、置信度。
2. View B（及更多观点）与证据、来源、置信度。
3. 冲突是事实差异、定义差异、时间差异、样本差异还是目标差异。
4. 每种做法适用的产品阶段、目标、预算、毛利、类目、站点和样本前提。
5. 每种做法何时应避免及主要风险。
6. 当前账户还缺什么数据。
7. 可逆、限时、带成功/停止指标的验证测试。

如果必须给当前操作建议，应把它标为“在现有条件下的优先测试路线”，不能伪装成唯一正确答案。

## 8. 推荐产物

收到实际新资料后，建议生成：

```text
data/processed/amazon_ads_skill/source_manifest.jsonl
data/processed/amazon_ads_skill/claim_review.jsonl
data/processed/amazon_ads_skill/source_validation_report.md
```

使用 `scripts/review_sources.py` 和 `references/15_source_review_schema.md` 生成上述产物。没有收到新资料或原子主张输入时，不要生成空的 `claim_review.jsonl`；仅需生成来源盘点时，报告状态必须是 `NOT_READY`。

## 9. 面向用户的回答要求

回答至少说明：

- 哪些主张得到支持；
- 哪些被可靠证据判定错误或过时，以及依据；
- 哪些只是缺乏支持；
- 哪些存在条件差异或仍有争议；
- 本轮实际检查了哪些来源，哪些没有检查；
- 对不确定项，不同做法及其条件、风险和验证计划。

## Common Mistakes

- 用来源数量代替来源独立性和证据质量。
- 把“没有找到证据”写成“已经证明错误”。
- 用当前官方功能说明去证明无法由官方文档支持的排名因果。
- 把不同站点、类目、阶段和目标下的案例直接比较。
- 静默删除少数观点或只保留与现有 skill 一致的说法。
- 没有覆盖记录却声称检查了全部文档。

## Quality Checklist

- 来源清单、去重簇和覆盖范围已记录。
- 重要说法已拆成原子主张并保留原文位置。
- 支持与反对证据都已检索。
- 时效敏感的平台事实已核对当前一手来源并记录日期。
- 判断状态符合定义，`confirmed_error` 有直接反证。
- 不确定和冲突观点没有被删除。
- 输出包含各路线的条件、风险、缺失数据和验证测试。
